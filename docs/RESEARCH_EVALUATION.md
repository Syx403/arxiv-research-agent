# ARA 任务质量评测

## 本轮验收原则

用户明确的优先级：影响检索方向的歧义先澄清；精确意图直接定位；简单问题采用摘要；复杂问题检索原文并回答实际问到的内容。允许为核心证据多花时间，但额外动作必须有收益。30 秒不是统一截止线。

首轮题集在 `tests/fixtures/research_acceptance.json`，包含 12 个场景、15 轮对话：4 个校准场景和 8 个验收场景。首轮验收题未用于对应修复前的调优，但部分论文出现在历史测试中，不能称为完全独立的盲测。发现问题后重跑同题属于回归，必须保留首轮记录。参考标签由开发助手事先对照 arXiv 原始来源整理，尚待用户校准，不冒充独立人工标注。2026-09-17 新增题集见本文末尾，在线结果尚未产生。

| 类别 | 数量 | 检查内容 |
|---|---:|---|
| 发现论文 | 4 | 指定 ID／标题、主题清晰但范围较宽、时效与数量要求 |
| 原文分析 | 3 | 算法机制、实现细节、跨论文比较 |
| 多轮对话 | 3 | 缩小范围、第一篇指代、切换研究主题 |
| 边界 | 2 | 无主题请求、原文证据不支持的夸大前提 |

网络故障、取消、预算、非法模型输出和版本缓存继续使用离线／数据库回归测试，不为模拟故障反复花模型额度。

## 两层评分，禁止混为总体准确率

1. **机械验收**：检查是否正确澄清、是否发生搜索／全文读取、数量／日期／指定论文约束、跨轮 ID 与版本、终止状态，以及展示引文与数据库原文的身份和字符位置一致性。脚本输出 `mechanical_pass`。这不证明内容完整、相关或可信。
2. **有来源的内容审阅**：对照每题 rubric 与原文，逐项判断主题相关性、关键内容覆盖、引用是否支持陈述、表达是否清楚、边界是否诚实。记录 `pass / partial / fail / pending` 和原因；不要使用系统自己的 verifier 作为独立评分者。首轮不使用付费 LLM judge。

开放发现题的参考论文是非穷尽锚点。返回其他符合条件的论文也可以合格；未标注论文不自动算错。只对明确指定的论文或可明确定位的任务设置强制 ID。最新论文的参考集合注明核对日期，不能当作整个 arXiv 的完整召回集合。

故障诊断要区分：查询设计 → 外部候选 → 语义筛选 → 排序展示 → 原文获取 → 片段召回 → 选句与打包 → 充分性 → 生成／引用核验。保存原始失败，后续修复是新版本的回归，不能覆盖原来的验收结果。

## 运行与成本

先启动 `make ui`。评测通过同一个本地 HTTP 接口执行，使用 Flash low/low；每个场景独立会话，场景内保留多轮上下文。原文和向量可复用，结果中记录缓存情况，所以单次耗时不能直接作为冷启动性能数据。

```sh
# 离线检查不调用真实模型
uv run pytest tests/unit/test_research_acceptance.py -q

# 在线校准；与 UI 共享已有累计 US$2 账本
uv run python -m scripts.eval_research \
  --split calibration --max-spend 0.30 \
  --output data/eval_outputs/research-acceptance/calibration

# 独立保存验收结果；运行之前确认服务已加载对应源码版本
uv run python -m scripts.eval_research \
  --split acceptance --max-spend 0.35 \
  --output data/eval_outputs/research-acceptance/acceptance
```

批次上限从已有预算内分配，不新增或重置总额度。每轮开始前预留本轮可能使用的最高额度；不足时保留未完成项目，不记为通过。进度在发送前保存请求 ID，中断后使用相同参数和输出目录恢复，避免重复收费；源码、题集或配置变化需要新目录。HTTP 会话与 trace 保留实际响应，`progress.json` 和 `summary.json` 记录执行情况。评测脚本没有读取或输出 API key 的逻辑。

## 当前已观察到的校准缺陷

- C3 要求两三篇但返回五篇：已增加规划中的数量约束、明确数量的程序校验，以及排序后的交付上限。候选召回不因此截断。模型摘要总览若引用了被移除的论文，不能继续展示。
- C4 显示完成，却遗漏原文已有的训练／梯度说明：相关原始 chunk 已召回，但选句只取少量同类事实，同时把同一原论文中标为 background 的互补证据过滤掉。已允许按多个实际问题选择更多完整源句，保留原论文的互补证据，强化充分性检查。证据 token 总预算不变。
- C3 曾因推理耗尽输出空间，执行一次格式恢复，造成明显额外延迟：作为后续性能问题保留，不以格式恢复成功冒充性能达标。
- C4 PDF 丢失公式上横线，使平均负载与实际负载无法区分；系统的核验也错误接受了方向相反的公式。材料获取现优先同版本官方 HTML，保存公式 alttext；保留 PDF 回退。处理指纹更新后重建索引，旧引用不删除。该题的失败和修复后回归分别保存。
- A4 原本只询问路由与溢出处理，规划器增加了“训练与推理分别处理”的要求，导致错误的证据不足。现将聚焦问题的验收范围固定在已消解的用户问题，整篇概览才允许扩展阅读提纲。

## 本轮开始前的校准建议（用户已确认）

先校准判断尺度，再增加陌生题，而不是仅扩大题目数或继续堆叠模块：

1. **匹配程度**：A2 的 Working Memory Hub 摘要明确是概念蓝图，INMS 主要讨论共享记忆；与长期记忆有关不等于直接满足长期记忆方案需求。应区分直接匹配、相关参考及证据限制，但不能对本来清晰的宽主题强行反问。用户未要求成熟实现时，也不能自动排除概念论文。
2. **答复范围**：A4—A6 已找到正确证据，仍需把结果组织成集中回答。默认只解释实际问到的机制；补充变体或实验必须解释其必要性，避免正文越长越像“深入”。
3. **否定前提的完成条件**：A8 的正确交付可能是“现有材料不能支持该说法”。应区分论文事实与证据覆盖边界，防止把合理的限定性陈述标为论文全局事实后反复否决。不能为了显示 complete 而编造不存在的证明。
4. **格式恢复与时延**：单独测量思考输出与结构化内容的预算分配，比较有无恢复的耗时与筛选质量。先保存基线，再决定改参数，避免同时更改判断标准和性能参数。

用户校准少量真实输出后，再补充未参与修复的新论文、新领域和多轮指代题。任务集样本不足以证明总体可靠性，也不应直接转换成简历中的总体准确率。


## 用户确认后的实施与回归

详细证据保存在 `data/eval_outputs/research-quality-20260916/review.json`。直接匹配数量、概念方案与实验成熟度、原文补查的完成条件、聚焦答复的边界已经按用户确认的尺度实施。新增 `tests/fixtures/research_quality.json`，包括 5 个针对性场景、6 轮交互，并加入有原文明确支持的正向核实题，避免把所有核实请求都做成拒答。

- 直接匹配结果不足用户要求的下限时触发有界补查；综述等相关参考另列。用户未要求成熟实现时，概念机制也可以直接匹配。
- `verify_claim` 对指定版本的现有解析材料做一次有界补查，记录真实输入范围和精确选句。负面结论限制于本次材料，不把未找到支持等同于证明命题为假。
- 答案先整段检查范围与重复，再核验保留句子的来源。重复只能引用更早保留的说明；不能用失败的可选编辑步骤跳过事实核验。主任务推理档位现在也适用于事实核验。
- 页面显示补查范围及结构化判断，并区分“省略补充／重复内容”和“事实核验失败”。未核验的补查自由文字总结保留在诊断记录，不作为页面技术结论。

开发中保留了几类真实失败：综述被当作独立方案凑数；无引用结论与过程说明触发假性 partial；逐句判断漏掉重复；补查选句结构不合法；非思考核验接受了上／下界颠倒。最后一类增加了一对真实来源对照：`I > a` 被写成上界时拒绝，写成下界时接受。途中正确版本的请求出现 DNS 故障，仅恢复未完成项，失败请求的预算预留没有抹去。早期补查格式失败没有保存完整非法字段，不能事后声称已确认是哪一个字段；现已补全结构约束、纠错上下文与诊断。

最终 `run-v6` 的 6 轮和 `comparison-v6` 的 1 轮使用相同 Python 源码指纹，全部通过机械检查。开发助手另外对照原文进行内容审阅，未发现本轮要求范围内的关键事实遗漏或错误；仍有少量句内重复，尚未取得独立人工标注。正文回答的 **15 个展示片段**逐一对照数据库论文身份、版本及字符位置，一致。

| 场景 | 最后观察 | 热缓存下单次耗时 |
|---|---|---:|
| 长期记忆方案 | 3 篇直接匹配，1 篇综述另列 | 7.5 秒 |
| Switch 路由和溢出 | 3 段核心说明，省略重复与可选变体 | 13.0 秒 |

缓存命中、样本量小和模型随机性限制了这些时间的意义。前两类发现题的最后重跑复用了模型判断缓存，但仍进行了外部获取；不能据此声称冷搜索只需 7 秒。主任务思考核验提高了部分题的时延，当前接受这一代价，尚未独立测量其准确率收益。

验证：**372 项离线测试通过，17 项跳过；本轮相关数据库检查 8 项通过**。Ruff、JavaScript 语法和 diff 检查通过。浏览器实际核对了分组卡片、补查范围及省略说明。

下一步应冻结这版判断尺度，再准备与修复案例不同的盲测问题，按发现、原文机制、多轮指代和证据边界分组。先由用户校准少量参考答案与允许的解释范围，随后执行预留测试集；不要把这一批开发回归的通过数写成简历总体准确率。宽主题召回、冷启动时延、较长论文的补查范围仍需要单独评测，而非继续增加模块。

## 2026-09-20 引用绑定修复与核验复用

本轮只调整已有正文阅读链路的修复和核验行为。用户认可前一轮解释后，同意先完成这项收尾，再整理项目经历。源代码摘要、固定初稿、原文片段、失败记录和在线结果保存在 `data/eval_outputs/citation-repair-20260920/`。

原问题是：原文已经包含所需信息，但初稿只引用了支持部分句子的片段。旧路径先补查原文再改写句子，既可能损失信息，也会使绑定整篇回答的核验缓存全部失效。现在在补查前，最多进行一次已有证据的引用绑定提议：只允许使用同一论文版本的已有片段，程序只替换引用标记，不改正文；提议仍须通过正常核验。证据确实不足或与论断矛盾时，不能靠换引用直接放行。结构化答案沿用其字段与引用一起修复的路径。

范围与覆盖检查仍每轮查看完整回答，并重新声明句子依赖。事实检查只接收该句、表头、实际依赖的前文、来源及问题；缓存键同步包含这些输入、来源内容和模型阶段配置。无范围检查的调用保留整篇回答作为上下文。修改前文条件、表头或证据会使相关检查失效；独立且未变化的句子可以复用。未核验的前提不能成为后续结论的依据。
